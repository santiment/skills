# Отчёт по тестированию score-CLI

Дата проверки: 2026-06-24
Что проверяли: командную утилиту `score` — клиент к двум бэкендам Santiment Score
(**Sanr** и **Arena**).

Этот отчёт написан простым языком. Если ты только начинаешь — читай сверху вниз,
здесь всё объясняется по шагам.

---

## 1. Коротко: что в итоге

- Написан большой набор тестов: **офлайн** (без интернета) и **живые** (реально
  ходят на серверы Sanr/Arena).
- Прогон с настоящим токеном пользователя: **55 тестов прошли (PASS), 20 пропущены
  (SKIP), 0 упали (FAIL)**.
- Пропущенные — это не ошибки. Они сознательно отключены, когда нет нужных доступов
  или когда тест мог бы испортить данные (см. раздел 6).
- По ходу проверки нашли **3 реальных особенности бэкенда**, о которых стоит знать
  (см. раздел 5). Это и есть главная польза живых тестов.

---

## 2. Как устроены тесты (два вида)

В Go тесты можно помечать «тегами сборки». Мы используем тег `integration` для
живых тестов, чтобы они не запускались случайно.

| Вид | Команда запуска | Нужен интернет? | Что проверяет |
|-----|-----------------|-----------------|---------------|
| Офлайн (unit) | `task test` | нет | чистую логику внутри программы |
| Живые (integration) | `task test-integration` | да | что команды реально работают с серверами |

Почему так: офлайн-тесты быстрые и надёжные (их можно гонять хоть на каждый коммит),
а живые показывают, что утилита по-настоящему общается с API.

---

## 3. Что проверили офлайн (без интернета)

Это «внутренняя кухня» утилиты — куски, которые нельзя честно проверить живым
запросом, потому что они про обработку данных, а не про сеть.

- **Разбор тела запроса** (`bodyFlags`): можно передать JSON через флаг `--data`,
  через файл `--data-file`, или через стандартный ввод (`-`). Проверили все три
  способа + ошибки (нет тела, кривой JSON, файл не найден).
- **Разбор ошибок API** (`apierr`): сервер может прислать ошибку в разных форматах
  (`{"message":...}`, `{"error":...}`, вложенный объект и т.д.). Проверили, что
  утилита аккуратно достаёт текст и код из всех вариантов, и не падает на «мусоре».
- **Каталог команд** (`describe`): утилита умеет выдавать машинно-читаемый список
  всех своих команд и кодов выхода. Проверили, что в списке есть все 16 команд и
  все коды выхода (0–7). Это страховка от рассинхрона: если кто-то добавит команду
  и забудет про каталог — тест это поймает.
- **Версия** (`version`): отдаёт корректный JSON с номером версии.
- **Аутентификация локально** (`auth set-token`): сохранение токена в конфиг-файл и
  чтение обратно (токен в выводе показывается замаскированным).
- **Конфиг** (`config`): приоритет настроек (флаг > переменная окружения > файл >
  значение по умолчанию), выбор профиля, ошибка на битом YAML.
- **HTTP-движок** (`httpx`): повтор запроса при ответах 429 и 5xx.

Все офлайн-тесты — **зелёные**.

## 4. Что проверили вживую (реальные запросы на серверы)

Здесь утилита по-настоящему ходит на `api.sanr.app` и `api-arena.santiment.net`.

### 4.1 Публичные чтения (без токена) — всё прошло
`markets list/filters/status`, `predictions list/merkle`, `leaderboards
forecasts/players`, `competitions list`, `pairs list/categories`, `prices`,
а также детальные запросы по id, взятым из списков (`predictions get`,
`leaderboards player ...`). Проверка здоровья обоих бэкендов (`health`) — тоже ок.

### 4.2 Чтения с токеном — токен рабочий
С настоящим токеном прошли:
- `profile get` — вернул реальные данные аккаунта;
- `profile notifications-status`;
- `pairs favorites` (этот эндпоинт требует вход).

То, что эти запросы вернули данные (а не «401 — не авторизован»), и есть
доказательство, что токен реально принимается сервером.

### 4.3 Коды выхода (контракт ошибок) — всё прошло
Утилита обещает стабильные коды возврата. Проверили на живых ответах:
- запрос несуществующего предсказания → **код 4** (не найдено);
- запрос с заведомо неверным токеном → **код 3** (нет авторизации);
- нечисловой id / кривой `--param` → **код 2** (ошибка ввода, без обращения к сети).

### 4.4 Команды входа (auth)
- `auth login` с неправильной подписью → сервер ответил ошибкой (как и должно
  быть), утилита корректно её показала.
- `auth refresh` и «оба бэкенда авторизованы» — **пропущены**, т.к. для них нужны
  refresh-токен и ключ Arena, которых в этот раз не было.

## 5. Что нашли по ходу (реальные особенности бэкенда)

Это самое ценное. Тесты сразу вскрыли расхождения с ожиданиями — значит, они
работают не «для галочки».

1. **`pairs favorites` требует авторизацию.** Без токена сервер отвечает
   `401 UNAUTHORIZED`. Сначала мы по ошибке считали его публичным — поправили,
   перенесли в группу «с токеном».

2. **`pairs aggregated` не работает с пустым фильтром.** Сервер отвечает
   `400 WRONG_SORT_OR_FILTER_FIELD`, и набор допустимых полей фильтра зависит от
   эндпоинта. Поэтому тест запускается только если задать корректный фильтр через
   переменную `SCORE_TEST_PAIRS_FILTER`, иначе пропускается (чтобы не «угадывать»).

3. **Arena `stakes` не проверяет ключ.** Запрос с заведомо неверным `--api-key`
   всё равно вернул данные (HTTP 200). То есть этот эндпоинт открыт. Тест, который
   ожидал ошибку на плохой ключ, мы убрали как неверный (он проверял несуществующее
   поведение сервера, а не саму утилиту).

4. **Портфель у аккаунта с токеном пуст.** Все запросы `portfolio *` вернули
   `401 ISSUER_NOT_FOUND`. Причина — в токене стоит отметка `GDPR` (аккаунт прошёл
   удаление данных), поэтому у него нет записи issuer/портфеля. Это **состояние
   данных аккаунта, а не ошибка утилиты**: сама команда корректно авторизуется и
   отправляет запрос. Поэтому тесты портфеля теперь считают такой ответ допустимым
   (помечают как «пропущено: у аккаунта нет данных»), и набор остаётся зелёным как
   для пустых, так и для заполненных аккаунтов.

---

## 6. Почему 20 тестов «пропущены» (это нормально)

Тест пропускается (SKIP), когда для него нет условий. Это защита, а не сбой:

- **Нет ключа Arena** (`ARENA_API_KEY`) → пропущены все чтения Arena
  (issuers, stakes, events, contracts) и проверка «оба бэкенда авторизованы».
- **Нет refresh-токена** (`SANR_REFRESH_TOKEN`) → пропущен `auth refresh`.
- **Не включены записи** (`SCORE_TEST_WRITES=1`) → пропущены все команды, которые
  что-то меняют (создание/обновление/закрытие предсказаний, ордера, депозиты и т.д.).
- **Аккаунт без портфеля** → пропущены 5 запросов портфеля (см. п. 5.4).
- **`profile gdpr` (удаление аккаунта)** → **никогда не вызывается**. Для него нет
  «волшебного флага», который бы его включил. Это сделано специально, чтобы тесты
  не могли случайно удалить аккаунт.

---

## 7. Про безопасность данных (важно)

Команды, которые **меняют** данные (создать/удалить/перевести деньги/изменить
профиль), защищены двумя «рубильниками»:

- `SCORE_TEST_WRITES=1` — включить обычные обратимые записи;
- `SCORE_TEST_DESTRUCTIVE=1` — дополнительно включить «опасные» (финансовые/
  необратимые).

Без этих переменных такие тесты не запускаются вообще. А тела запросов для записи
берутся из переменных окружения (например `SCORE_TEST_PREDICTION_BODY`), чтобы
утилита не отправляла «придуманные» данные, которые могут что-то сломать.

В этой проверке записи **не запускались** — мы трогали только чтение.

## 8. Как повторить проверку

```bash
# 1) Офлайн (быстро, без интернета):
task test

# 2) Живые публичные чтения (без токенов):
task test-integration

# 3) Живые чтения с токеном Sanr:
SANR_TOKEN='…' task test-integration

# 4) Добавить Arena:
SANR_TOKEN='…' ARENA_API_KEY='…' task test-integration

# 5) Полный прогон с записями (только на тест-стенде!):
SANR_TOKEN='…' SANR_REFRESH_TOKEN='…' ARENA_API_KEY='…' \
  SCORE_TEST_WRITES=1 \
  SCORE_TEST_PROFILE_BODY='{…}' SCORE_TEST_PREDICTION_BODY='{…}' \
  task test-integration
```

Полный список переменных окружения — в шапке файлов
`internal/app/score/integration_helpers_test.go` и
`internal/app/score/integration_write_test.go`.
