# Отчёт по тестированию score-CLI

Дата проверки: 2026-06-24
Что проверяли: командную утилиту `score` — клиент к двум бэкендам Santiment Score
(**Sanr** и **Arena**).

Отчёт написан простым языком. Читай сверху вниз.

---

## 1. Коротко: что в итоге

- Написан большой набор тестов: **офлайн** (без интернета) и **живые** (реально
  ходят на серверы Sanr/Arena).
- С реальным токеном и включённой записью: **70 тестов прошли (PASS),
  12 пропущены (SKIP), 0 упали (FAIL)**.
- Проверены и чтения, и **записи** (создание/изменение/закрытие предсказания,
  обновление профиля) — на живом сервере, с очисткой за собой.
- **Один и тот же токен работает для обоих бэкендов** (Sanr и Arena) — подтверждено.
- Оставшиеся 12 пропусков требуют данных, которых нет: аккаунт с портфелем и
  реальные тела финансовых запросов (см. раздел 6).

Модель авторизации: CLI работает по **одному долгоживущему API-ключу** (~5 лет).
Механизма refresh нет — поэтому теста на refresh тоже нет.

---

## 2. Как устроены тесты (два вида)

| Вид | Команда запуска | Нужен интернет? | Что проверяет |
|-----|-----------------|-----------------|---------------|
| Офлайн (unit) | `task test` | нет | чистую логику внутри программы |
| Живые (integration) | `task test-integration` | да | что команды реально работают с серверами |

Живые тесты помечены тегом `integration`. Если для теста нет нужного доступа —
он **пропускается** (SKIP), а не падает.

## 3. Что проверили офлайн (без интернета)

- **Разбор тела запроса** (`--data`, `--data-file`, stdin + ошибки).
- **Разбор ошибок API** — разные форматы ошибок сервера, плюс «мусор».
- **Каталог команд** (`describe`) — все 16 команд и все коды выхода (0–7).
- **Версия** (`version`).
- **Сохранение токена** (`auth set-token`) в конфиг и чтение обратно (замаскировано).
- **Конфиг** — приоритет настроек, выбор профиля, ошибка на битом файле.
- **HTTP-движок** — повтор запроса при ответах 429 и 5xx.

Все офлайн-тесты — зелёные.

## 4. Что проверили вживую (реальные запросы)

### 4.1 Публичные чтения Sanr (без токена) — прошли
`markets list/filters/status`, `predictions list/merkle`, `leaderboards
forecasts/players` (+ детальные по игроку), `competitions list`,
`pairs list/categories`, `prices`, `predictions get`, `health`.

### 4.2 Чтения Sanr с токеном — прошли
`profile get` (реальные данные), `profile notifications-status`, `pairs favorites`.

### 4.3 Чтения Arena (с тем же токеном) — прошли
`issuers list/get`, `stakes`, `events`, `contracts list`, пагинация (`--limit`),
и Hyperliquid-подкоманды `issuers hyperliquid metrics|positions|trades|snapshots`
(терпимы к отсутствию HL-данных у обычного issuer).

### 4.4 Коды выхода (контракт ошибок) — прошли
- несуществующее предсказание → код 4 (не найдено);
- неверный токен → код 3 (нет авторизации);
- нечисловой id / кривой `--param` → код 2 (ошибка ввода).

### 4.5 Записи (реально меняют данные) — прошли
Запускаются только с флагом `SCORE_TEST_WRITES=1`.
- **Предсказание целиком:** `create` → `get` → `update` (take-profit) → `close`.
  Тело создаётся автоматически из реального `marketId` и направления. В прогоне
  предсказание создалось, изменилось и закрылось — тест убирает за собой.
- **Профиль:** `profile update` с «пустой» правкой (повтор текущего значения флага).

### 4.6 Команды auth
`auth login` с неправильной подписью → сервер отклонил, утилита корректно показала
ошибку. `auth status` с токеном → оба бэкенда «авторизованы».

## 5. Что нашли по ходу (реальные особенности)

1. **Один токен — на оба бэкенда.** Sanr-JWT принимается и как `ARENA_API_KEY`
   (x-api-key). То есть достаточно одного ключа.
2. **`pairs favorites` требует авторизацию** (без токена → 401).
3. **`pairs aggregated` не работает с пустым фильтром** (`400
   WRONG_SORT_OR_FILTER_FIELD`) — запускается только при заданном
   `SCORE_TEST_PAIRS_FILTER`.
4. **Hyperliquid — это подкоманды:** `issuers hyperliquid <metrics|positions|
   trades|snapshots> <id>`, а не отдельные команды `issuers`. (Изначально тест
   звал неверный путь — поправлено.)
5. **Arena `stakes` не проверяет ключ** — отдаёт данные с любым. Тест на «плохой
   ключ» убрали как неверный.
6. **Портфель текущего аккаунта пуст** — `portfolio *` → `401 ISSUER_NOT_FOUND`
   (аккаунт прошёл GDPR-очистку). При этом предсказания у него создаются нормально
   — значит дело в данных аккаунта, а не в утилите.

---

## 6. Почему осталось 12 пропусков и что их разблокирует

| Что пропущено | Сколько | Что нужно |
|---|---|---|
| Чтения портфеля (`portfolio *`) | 5 | **токен аккаунта, у которого есть портфель** (у текущего его нет) |
| Финансовые записи (distribution-save, order, deposit, withdrawal, recalc, disable-notifications ×2) | 7 | **`SCORE_TEST_DESTRUCTIVE=1` + реальные JSON-тела** |

Почему финансовые тела не «выдуманы»: в них суммы денег, цены активов и id
портфеля — реальные данные, двигающие средства на аккаунте. Их нужно снять с
веб-клиента (вкладка Network в браузере), а не угадывать.

`profile gdpr` (удаление аккаунта) — теста нет вообще, он не должен запускаться.

---

## 7. Про безопасность данных

- `SCORE_TEST_WRITES=1` — обычные обратимые записи (предсказания, профиль);
- `SCORE_TEST_DESTRUCTIVE=1` — дополнительно «опасные» (финансовые).

Без них такие тесты не запускаются. Предсказание после создания закрывается тем же
тестом.

---

## 8. Как повторить проверку

```bash
# Офлайн (быстро, без интернета):
task test

# Живые публичные чтения (без токенов):
task test-integration

# Полный прогон чтений + записей (один токен на оба бэкенда):
SANR_TOKEN='…' ARENA_API_KEY='…' SCORE_TEST_WRITES=1 task test-integration
#   (ARENA_API_KEY = тот же токен, что SANR_TOKEN)

# + финансовые записи (только осознанно, на тест-стенде):
SANR_TOKEN='…' ARENA_API_KEY='…' SCORE_TEST_WRITES=1 SCORE_TEST_DESTRUCTIVE=1 \
  SCORE_TEST_DISTRIBUTION_BODY='{…}' SCORE_TEST_ORDER_BODY='{…}' … \
  task test-integration
```

Полный список переменных — в шапке файлов
`internal/app/score/integration_helpers_test.go` и `integration_write_test.go`.
