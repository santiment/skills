# Отчёт по тестированию score-CLI

Дата проверки: 2026-06-24
Что проверяли: командную утилиту `score` — клиент к двум бэкендам Santiment Score
(**Sanr** и **Arena**).

Отчёт написан простым языком. Читай сверху вниз.

---

## 1. Коротко: что в итоге

- Написан большой набор тестов: **офлайн** (без интернета) и **живые** (реально
  ходят на серверы Sanr/Arena).
- С реальным Sanr-токеном и включённой записью: **57 тестов прошли (PASS),
  16 пропущены (SKIP), 0 упали (FAIL)**.
- Реально проверены и **записи**: создание/изменение/закрытие предсказания и
  обновление профиля — на живом сервере, с очисткой за собой.
- Оставшиеся пропуски — это эндпоинты, которым нужны данные, которых пока нет
  (ключ Arena, аккаунт с портфелем, тела финансовых запросов). См. раздел 6.
- По ходу нашли несколько реальных особенностей бэкенда (раздел 5).

Модель авторизации: CLI работает по **одному долгоживущему API-ключу** (Sanr JWT,
срок ~5 лет). Механизма refresh нет — поэтому теста на refresh тоже нет.

---

## 2. Как устроены тесты (два вида)

| Вид | Команда запуска | Нужен интернет? | Что проверяет |
|-----|-----------------|-----------------|---------------|
| Офлайн (unit) | `task test` | нет | чистую логику внутри программы |
| Живые (integration) | `task test-integration` | да | что команды реально работают с серверами |

Живые тесты помечены тегом `integration`, чтобы не запускаться случайно. Если для
живого теста нет нужного доступа — он **пропускается** (SKIP), а не падает.

## 3. Что проверили офлайн (без интернета)

- **Разбор тела запроса** (`--data`, `--data-file`, stdin + ошибки).
- **Разбор ошибок API** — разные форматы ошибок сервера, плюс «мусор».
- **Каталог команд** (`describe`) — все 16 команд и все коды выхода (0–7).
- **Версия** (`version`).
- **Сохранение токена** (`auth set-token`) в конфиг и чтение обратно (замаскировано).
- **Конфиг** — приоритет настроек, выбор профиля, ошибка на битом файле.
- **HTTP-движок** — повтор запроса при ответах 429 и 5xx.

Все офлайн-тесты — зелёные.

## 4. Что проверили вживую (реальные запросы)

### 4.1 Публичные чтения (без токена) — прошли
`markets list/filters/status`, `predictions list/merkle`, `leaderboards
forecasts/players` (+ детальные по игроку), `competitions list`,
`pairs list/categories`, `prices`, `predictions get` (по реальному id),
`health` (оба бэкенда).

### 4.2 Чтения с токеном — токен рабочий
`profile get` (вернул реальные данные), `profile notifications-status`,
`pairs favorites`. Успех = токен принят сервером.

### 4.3 Коды выхода (контракт ошибок) — прошли
- несуществующее предсказание → код 4 (не найдено);
- неверный токен → код 3 (нет авторизации);
- нечисловой id / кривой `--param` → код 2 (ошибка ввода).

### 4.4 Записи (реально меняют данные) — прошли
Запускаются только с флагом `SCORE_TEST_WRITES=1`.
- **Предсказание целиком:** `create` → `get` (проверка) → `update` (take-profit) →
  `close`. Тело создаётся автоматически из реального `marketId` (берётся из
  `markets list`) и направления `up`. В прогоне создалось предсказание, было
  изменено и закрыто — то есть весь жизненный цикл работает, и тест убирает за
  собой.
- **Профиль:** `profile update` с «пустой» правкой (повтор текущего значения
  флага) — ничего не ломает, но проверяет, что запись проходит.

### 4.5 Команды auth
`auth login` с неправильной подписью → сервер отклонил (как и должно), утилита
корректно показала ошибку.

## 5. Что нашли по ходу (реальные особенности бэкенда)

1. **`pairs favorites` требует авторизацию** (без токена → 401). Перенесли в группу
   «с токеном».
2. **`pairs aggregated` не работает с пустым фильтром** (`400
   WRONG_SORT_OR_FILTER_FIELD`). Запускается только при заданном валидном фильтре
   (`SCORE_TEST_PAIRS_FILTER`).
3. **Arena `stakes` не проверяет ключ** — отдаёт данные с любым `--api-key`. Тест,
   ожидавший ошибку на плохой ключ, убрали как неверный.
4. **Портфель текущего аккаунта пуст** — все `portfolio *` → `401 ISSUER_NOT_FOUND`,
   потому что аккаунт прошёл GDPR-очистку. При этом **предсказания у этого же
   аккаунта создаются нормально** — то есть это про данные аккаунта, а не про
   утилиту. Тесты портфеля помечают такой ответ как «пропуск: нет данных».

---

## 6. Почему 16 тестов пропущены и что их разблокирует

| Что пропущено | Сколько | Что нужно, чтобы прогнать вживую |
|---|---|---|
| Чтения Arena (issuers/stakes/events/contracts) + «оба авторизованы» | 4 | **`ARENA_API_KEY`** |
| Чтения портфеля (`portfolio *`) | 5 | **токен аккаунта, у которого есть портфель** |
| Финансовые/портфельные записи (distribution-save, order, deposit, withdrawal, recalc, disable-notifications ×2) | 7 | **`SCORE_TEST_WRITES=1` (+ для опасных `SCORE_TEST_DESTRUCTIVE=1`) и реальные JSON-тела** |

Почему финансовые тела не «выдуманы»: в них суммы, цены активов и id портфеля —
это реальные данные, которые двигают средства/позиции на аккаунте. Их нужно снять
с веб-клиента (вкладка Network в браузере), а не угадывать.

`profile gdpr` (удаление аккаунта) — теста нет вообще, он не должен запускаться.

---

## 7. Про безопасность данных

Команды, меняющие данные, защищены двумя «рубильниками»:
- `SCORE_TEST_WRITES=1` — обычные обратимые записи (предсказания, профиль);
- `SCORE_TEST_DESTRUCTIVE=1` — дополнительно «опасные» (финансовые).

Без них такие тесты не запускаются. Предсказание после создания **закрывается**
тем же тестом.

---

## 8. Как повторить проверку

```bash
# Офлайн (быстро, без интернета):
task test

# Живые публичные чтения (без токенов):
task test-integration

# Живые чтения с токеном Sanr:
SANR_TOKEN='…' task test-integration

# + чтения Arena:
SANR_TOKEN='…' ARENA_API_KEY='…' task test-integration

# + записи (предсказания и профиль реально создаются/меняются):
SANR_TOKEN='…' SCORE_TEST_WRITES=1 task test-integration

# + финансовые записи (только осознанно, на тест-стенде):
SANR_TOKEN='…' SCORE_TEST_WRITES=1 SCORE_TEST_DESTRUCTIVE=1 \
  SCORE_TEST_DISTRIBUTION_BODY='{…}' SCORE_TEST_ORDER_BODY='{…}' … \
  task test-integration
```

Полный список переменных — в шапке файлов
`internal/app/score/integration_helpers_test.go` и `integration_write_test.go`.
